# Архитектура и границы гарантий

## Модули

`common.py` — конфигурация, проверки доступа, безопасные строки и общий limiter. `store.py` — SQLite и транзакции. `api.py` — узкие клиенты HTTPX. `planner.py` — преобразование сообщений в независимые задания. `media.py` — потоковое скачивание через curl с закреплённым публичным адресом. `bridge.py` — опрос, команды, темы, история, доставка, watchdog. `updates.py` — проверка версий. `__main__.py` — локальные проверки, probe, блокировка процесса, резервное копирование и запуск.

Библиотека VK SDK не используется. Вместо неё реализован небольшой набор нужных HTTP-методов. Поведение близко к telemax, но это не перенос SDK MAX и не обещание идентичной внутренней реализации. Код telemax 3.5.2 изучен для сохранения пользовательских решений; его репозиторий не изменялся.

## Долговечность и подтверждения

```text
VK getLongPollHistory(pts)
  → транзакция: inbox + new_pts + имена
  → планировщик: текстовые задания и задания вложений
  → общая очередь отправок Telegram
  → подтверждение API + таблица соответствий

Telegram getUpdates(offset)
  → проверка owner + group
  → транзакция: inbox + следующий offset
  → подготовка VK-задания + постоянный random_id
  → при необходимости скачивание и загрузка вложения
  → messages.send
  → транзакция: соответствия + done + отдельное markAsRead при reply
```

Ни одна SQLite-транзакция не пересекает `await`. В SQLite включены WAL, `synchronous=FULL`, foreign keys. Фиксация курсора без сохранения соответствующих входящих не допускается. Ошибка диска/БД не превращается в молчаливое продвижение курсора. Пропуск до долговечной фиксации зависит от способности источника повторно выдать данные; это не абсолютная гарантия сохранности.

Перед внешним созданием сообщения фиксируется intent `effect=1`. При нормальном подтверждении результат сохраняется вместе с завершением. При сетевом сбое, где эффект мог произойти, используется `uncertain`; при явном отказе — `dead` либо ограниченный повтор. Перезапуск переводит прерванные задания с effect в uncertain, остальные — обратно в pending. Даже сбой между установкой intent и реальной отправкой может привести к консервативному uncertain.

В VK `random_id` создаётся один раз для задания, сохраняется в базе и повторно используется при ручном повторе. Период хранения и область серверной дедупликации не считаются бесконечными. В Telegram общего ключа идемпотентности сообщений в этом протоколе нет, поэтому потерянное подтверждение не повторяется вслепую. Уведомления бота тоже являются заданиями; при общей недоступности Telegram они не могут быть доставлены немедленно. Журнал и локальная база остаются источниками диагностики.

## Очерёдность

Внутри конкретного peer и lane поддерживается порядок постановки: старое pending/running/uncertain препятствует обгону в той же lane. Для текста и файлов используются разные lane: независимость текста от медиа намеренная, поэтому общего тотального порядка всех частей сообщения нет. Разные диалоги обрабатываются параллельно. `dead` не блокирует следующие сообщения; проблемную часть видно отдельно.

Живые сообщения приоритетнее исторических. Исходящие команды и ответы имеют повышенный приоритет. Все Telegram-темы делят один rate limiter; серверный `retry_after` откладывает другие отправки тоже. После уже начатого ожидания limiter команда может ждать своего разрешённого слота; абсолютная мгновенность административных команд не обещается.

## Соответствия и защита от эха

Основной источник идентичности VK — `peer_id` + `conversation_message_id`, с резервом глобального `id`. В одной базе только один VK-аккаунт, один Telegram-бот, группа и владелец; изменение этой комбинации отвергается. Много Telegram-сообщений могут указывать на одно VK-сообщение. Привязка reply проверяется в пределах peer, чтобы ответ не ушёл в другой диалог.

В таблице `echoes` сохраняются random_id и подтверждённые ID исходящих. Коррелированное событие VK не зеркалируется обратно. Другие собственные сообщения из сайта/приложения VK зеркалируются. При раннем собственном событии во время незавершённой отправки планирование откладывается до получения результата, насколько позволяет наличие корреляции. Никакой общей фильтрации всех `out=1` нет.

При потере ответа без идентификатора в событии абсолютное устранение эха не гарантируется. Это частный случай общего ограничения неизвестного результата отправки.

## История и восстановление

Первый сохранённый pts задаёт начало наблюдения. Старые события, попавшие как изменение старого сообщения, не превращаются в неявный импорт. Часы сервера должны быть корректны: фильтрация даты использует небольшой допуск на целые секунды.

`/history all` использует `messages.getHistory` страницами до 200, обратное движение по глобальному ID и контроль прогресса. Стартовый anchor фильтруется локально. Страницы сохраняются атомарно с прогрессом. Полученный архив отправляется по исходным датам от старых сообщений к новым; дедупликация использует соответствия и уникальные ключи заданий. Одновременные правки/удаления, недоступные куски и ограничения приложения означают, что это не транзакционный снимок базы VK.

Ошибка слишком старого pts приводит к новому курсору плюс отдельной сверке диалогов с последнего успешного опроса, с временным перекрытием. Список диалогов читается с перекрытием страниц, однако его одновременное изменение может влиять на полноту. Нельзя восстановить сообщение, появившееся и удалённое во время отсутствия моста, если API больше его не отдаёт. Изменения/удаления старых сообщений не синхронизируются в этой версии.

История сначала сохраняется, затем отправляется. Если даже текстовый снимок всего архива не помещается в бюджет БД, сканирование останавливается до изменения бюджета/освобождения места; «вся история» не означает игнорирование конечных ресурсов сервера.

## Скачивание и секреты

Секреты в отдельных файлах 600; в запросы VK они входят в тело POST. Telegram использует токен в URL по своему API, поэтому журналы httpx/httpcore отключены; наружу выводятся нормализованные ошибки без исходного URL, тела запроса, токена или непроверенного сообщения внешнего сервера.

Для получения VK-вложений проверяются схема HTTPS, порт, отсутствие пользовательских credentials, публичность всех DNS-адресов и конечная цель каждого редиректа. Curl вызывается с `--resolve`, чтобы подключаться к уже проверенному адресу, не выполняя второе DNS-разрешение. URL передаётся в конфигурацию через stdin, не в аргумент процесса. Автоматические редиректы, прокси окружения, `.curlrc` и globbing отключены. Есть независимый потоковый предел, контроль свободного места, тайм-ауты, число редиректов и проверка длины. Файл удаляется после обработки. TLS и реальная маршрутизация в локальных тестах не имитируют свойства настоящей сети.

Upload URL принимаются только из ответа авторизованного VK API и проходят allowlist доменов, HTTPS и проверку порта. Это другая модель, чем скачивание произвольного media URL: транспорт HTTPX использует выбранный VK-прокси и обычное DNS. Allowlist нельзя расширять без проверки нового адреса поставщика.

База содержит текст переписки и данные заданий **без прикладного шифрования**. Права каталога ограничивают локальный доступ, но не заменяют шифрование диска/бэкапов. Старые завершённые задания и сырые payload очищаются; компактные отметки дедупликации, links, echoes и неразрешённые ошибки сохраняются. Поэтому размер базы не становится строго постоянным навсегда: для этого и предусмотрен бюджет и ручное обслуживание.

## Известные границы пилота

Нет нативных голосовых/видеозвонков, синхронизации правок и удаления, общего UI для нескольких пользователей, локального Bot API сервера, OAuth-регистратора, автоматической установки обновлений, автоматического переноса тем из telemax и универсальной миграции схемы.

Нет отдельной команды «подтвердить uncertain доставленным и ввести правильный remote ID». Неопределённый результат без повтора требует ручной диагностики базы при остановленном сервисе. Не заявляется, что это полнофункциональная production-платформа с завершённым управлением всеми отказами. Текущая версия предназначена для проверенного запуска на одном аккаунте после приёмочных тестов.
