# Установка и эксплуатация TeleVK 0.1.1

## 1. Подготовить отдельный Telegram-интерфейс

В BotFather создай **нового** бота через `/newbot`. Не используй токен telemax: два потребителя `getUpdates` одного бота будут конфликтовать. Создай отдельную закрытую группу, включи темы, добавь нового бота администратором с разрешением управления темами. Администратор-бот получает обычные сообщения группы; отключение Privacy Mode не является обязательной дополнительной настройкой для такой конфигурации. Источник: [Telegram FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).

Нужны два числовых идентификатора: твой user ID и **ID новой группы**, а не существующей группы telemax. Собственный user ID можно взять из своей текущей конфигурации telemax. Новому сервису нельзя передавать ID прежней группы по инерции.

Для получения идентификаторов без стороннего бота есть локальная утилита. После установки зависимостей, но **до запуска TeleVK**, напиши `/ids` от своего аккаунта в новой группе и выполни:

```bash
cd /opt/televk
sudo -u televk .venv/bin/python deploy/telegram_ids.py
```

Она попросит токен нового бота и адрес прокси, прочитает ожидающие обновления и выведет только пары user ID / group ID и ID темы. Текст переписки и токен не выводятся. Запускать рядом с работающим получателем обновлений нельзя. Утилита не продвигает offset; остаточные команды будут проигнорированы по времени первого подключения или обработаны как неизвестные. Если бот возвращает несколько пар, выбирай свой аккаунт и новую группу. Не отправляй секреты в саму группу.

Если группа имеет участников кроме тебя, они смогут прочитать уже пересланные сообщения. Проверка sender ID ограничивает отправку через мост, а не видимость сообщений участникам группы. Поэтому закрытая группа только для тебя и бота — подходящая конфигурация.

## 2. Пользовательский доступ VK — обязательная внешняя предпосылка

Нужен токен пользователя, которому разрешены нужные операции Messaging API. Работоспособность `users.get` недостаточна: это проверка профиля, не переписки. Групповой токен обслуживает сообщения сообщества и не заменяет пользовательский токен для всех личных диалогов.

Используй способ выдачи токена, разрешённый VK для выбранного приложения и твоего аккаунта. Наличие обычного приложения VK ID само по себе не является подтверждением доступа к личной переписке. Этот релиз не включает автоматическую регистрацию приложения, извлечение браузерных cookies или использование чужого application ID. Утверждать, что новое произвольное приложение получит разрешение `messages`, оснований нет.

Предметная проверка выполняется самим пакетом. `probe` проверяет:

```text
Telegram: getMe, getChat, getChatMember, getWebhookInfo
VK: users.get, messages.getConversations, messages.getHistory,
    messages.getLongPollServer, messages.getLongPollHistory
```

`probe --send-test` дополнительно проверяет `messages.send` и чтение результата через `messages.getById`. Получатель — только ID пользователя, который вернул `users.get`, то есть его «Избранное». Отправка другим людям при диагностике не выполняется. Факт прочтения собеседником этим тестом не проверяется.

Для фото и документов нужны также соответствующие операции получения upload URL, загрузки и сохранения файла. Их можно проверить отдельными флагами ниже. Успешный текстовый тест не доказывает работоспособность загрузки файлов.

Частые причины остановки: отказ в конкретном методе, неверный/отозванный токен, отсутствующий `pts`, формат ответа, не соответствующий ожидаемой схеме, запрет на чтение конкретной беседы. Диагностика показывает метод и код VK, но не секретный запрос. Код 5 обычно обрабатывается как отказ токена; коды 7/15/20 и любые другие отказы нужно разбирать по **конкретному методу и условиям приложения**, не считать их автоматически решаемыми новым токеном.

Если проверка чтения личных сообщений не проходит, не запускай постоянно падающий сервис: сначала должен быть решён доступ приложения. TeleVK не может выдать себе дополнительные права. Источник структуры методов: [официальная схема VK](https://github.com/VKCOM/vk-api-schema/blob/master/messages/methods.json).

## 3. Подготовить Linux и репозиторий GitHub

Инструкция ориентирована на отдельную установку в `/opt/televk` под systemd. Существующий telemax не переносится и не обновляется. Требуется Python 3.11 или новее, модуль venv, curl с HTTPS, Git и системные CA-сертификаты.

На Debian/Ubuntu:

```bash
sudo apt-get update
sudo apt-get install -y python3 python3-venv curl ca-certificates tzdata git
python3 --version
```

Если системный Python старше 3.11, сначала установи поддерживаемую версию штатным способом своей ОС. Не заменяй `/usr/bin/python3` вручную. Установщику можно передать существующий новый интерпретатор через `PYTHON_BIN`, например `sudo env PYTHON_BIN=/usr/bin/python3.12 bash deploy/install.sh` — только если он действительно установлен.

### 3.1. Wheelhouse формируется на ПК, а не на HTPC

HTPC версии 0.1.1 **не обязан иметь доступ к PyPI**. В репозитории должен находиться каталог `wheelhouse/` с wheel-файлами закреплённых зависимостей и `wheelhouse/SHA256SUMS`.

На Windows-ПК с доступом к PyPI, из корня репозитория:

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\prepare-wheelhouse.ps1
```

Если Windows не знает команду `py`, предварительно задай `$env:PYTHON="python"` (или полный путь к установленному `python.exe`) и повтори команду.

Скрипт вызывает `pip download` по `requirements.txt` + `constraints.txt`, разрешает только binary wheels, проверяет, что они переносимы (`py3-none-any`), и создаёт SHA-256 манифест. После этого:

```powershell
git status
git add .
git commit -m "TeleVK 0.1.1: offline wheelhouse and GitHub deployment"
git push
```

Подробный GitHub-процесс: `docs/GITHUB_WORKFLOW.md`.

### 3.2. Установка с GitHub на HTPC

Для первой установки:

```bash
git clone <URL_ТВОЕГО_РЕПОЗИТОРИЯ> televk
cd televk
sudo bash deploy/install.sh
```

Установщик создаёт отдельного системного пользователя `televk`, каталог кода `/opt/televk`, каталог настроек `/etc/televk` и состояния `/var/lib/televk`; проверяет SHA-256 wheelhouse, создаёт virtualenv, устанавливает зависимости **только локально через `pip --no-index`**, запускает тесты и устанавливает unit. Он **не запускает и не включает автозапуск** сервиса.

Онлайн-режим существует только как явный выбор `--online`; по умолчанию сетевого обращения pip к package index нет.

### 3.3. Твой текущий случай: продолжение прерванной 0.1.0

Если прежний `install.sh` остановился именно на скачивании Python-пакетов, то обычно уже существует `/opt/televk`, а `/etc/televk` и `/var/lib/televk` созданы как пустые каталоги. После того как обновлённый репозиторий и wheelhouse находятся на HTPC:

```bash
git pull --ff-only
sudo bash deploy/install.sh --resume
```

`--resume` удаляет и пересоздаёт **только** незавершённый `/opt/televk`. Он сохраняет `/etc/televk` и `/var/lib/televk` и намеренно откажется работать, если уже существует `/etc/televk/config.json`, `/var/lib/televk/bridge.sqlite3` или `/etc/systemd/system/televk.service`. То есть режим предназначен только для прерванной первой установки, а не для обновления живого сервиса.

Входящие TCP-порты мост не открывает. Для обычной работы нужны исходящие HTTPS-соединения к Telegram, VK/CDN и GitHub. PyPI на HTPC не требуется ни для установки, ни для `/updates`.

## 4. Заполнить конфигурацию локально

```bash
cd /opt/televk
sudo -u televk .venv/bin/python -m televk --config /etc/televk/config.json init
```

Ответы на запросы: твой user ID; ID новой группы; прокси Telegram или пустая строка; токен нового Telegram-бота; пользовательский токен VK; **`/var/lib/televk` как каталог состояния**. Последний путь важен: unit разрешает запись именно туда. Не оставляй `state` по умолчанию при установке с предлагаемым системным unit.

Файлы секретов создаются отдельно:

```text
/etc/televk/config.json
/etc/televk/secrets/telegram.token
/etc/televk/secrets/vk.token
```

Настройки и секреты принадлежат `televk`, файлы имеют права 600. Конфигурация читается при старте; изменения требуют перезапуска. Пример всех полей — `config.example.json`, но это **не рабочий конфиг** с твоими ID.

| Параметр | По умолчанию | Значение |
|---|---:|---|
| `VK_API_VERSION` | `5.199` | Версия вызовов; не менять автоматически по номеру schema-пакета |
| `VK_POLL_SECONDS` | `2.0` | Пауза опроса изменений, когда нет продолжения |
| `TG_SEND_INTERVAL` | `3.1` | Общий интервал отправок во всю группу, не на тему |
| `VK_API_INTERVAL` | `0.36` | Разведение вызовов VK; серверные отказы и паузы тоже соблюдаются |
| `WORKERS` | `4` | Рабочие задачи; медиа дополнительно ограничены двумя слотами |
| `MAX_FILE_MB` | `50` | Локальный предел файла в MiB; облачный Telegram накладывает свои пределы |
| `MAX_PENDING` | `20000` | Мягкий порог, при котором приостанавливаются получение VK и импорт истории |
| `MIN_FREE_MB` | `256` | Минимальный остаток диска, плюс резерв при скачивании |
| `MAX_DB_MB` | `2048` | Бюджет основной SQLite и служебных файлов |
| `RETENTION_DAYS` | `30` | Очистка payload обработанных входящих и завершённых заданий |
| `UPDATE_CHECK_HOURS` | `168` | Проверка новых версий; `0` отключает автоматическую проверку |
| `TIMEZONE` | `Europe/Amsterdam` | Часовой пояс отображаемых дат |

Контрольные Telegram-команды продолжают приниматься при превышении `MAX_PENDING`. Порог не является абсолютно жёстким числом заданий: один пакет событий или сообщение с несколькими частями может его превысить; записи владельца из Telegram сохраняются отдельно от приостановки VK/архива. Жёсткая практическая граница — доступный диск и бюджет базы. При нехватке диска даже команды нельзя надёжно сохранить; тогда нужны журнал systemd и локальное исправление.

Прокси независимы: `TG_PROXY` для Telegram, `VK_PROXY` для VK API; текущая реализация `/updates` использует тот HTTPX-клиент, который уже создан для VK, поэтому GitHub-проверки идут через тот же `VK_PROXY`, если он задан. Внешние переменные `HTTP_PROXY`/`HTTPS_PROXY` игнорируются. **Скачивание VK-вложений выполняется напрямую через curl с закреплённым проверенным IP**, а не через `VK_PROXY`. Если на сервере CDN доступны только через прокси, это отдельное ограничение этой версии: включать обход защиты не следует. Загрузка документов из Telegram в VK идёт по `VK_PROXY` через HTTPX.

## 5. Проверки до запуска

```bash
cd /opt/televk
sudo -u televk .venv/bin/python -m televk --config /etc/televk/config.json check
sudo -u televk .venv/bin/python -m televk --config /etc/televk/config.json probe
sudo -u televk .venv/bin/python -m televk --config /etc/televk/config.json probe --send-test
```

`check` выполняется без сетевых вызовов: конфигурация, права секретов, наличие curl/SOCKS-зависимости и SQLite integrity check. `probe` не отправляет тестовые сообщения, пока не указан `--send-test`. Проверка отправки хранит только отпечаток токена; после смены токена она нужна заново.

Загрузку можно проверить обычной небольшой фотографией JPEG и текстовым документом, доступными пользователю `televk`:

```bash
sudo -u televk .venv/bin/python -m televk --config /etc/televk/config.json \
  probe --send-test --photo /tmp/televk-probe.jpg --document /tmp/televk-probe.txt
```

Файлы для этого примера ты создаёшь самостоятельно. Эта команда отправит ещё несколько тестовых сообщений в собственное «Избранное» VK. После неё проверь файлы визуально там. Разрешение чтения устанавливается для конкретного аккаунта, бота, группы и владельца; база не переносится на другую комбинацию ID без отдельной миграции.

## 6. Первый запуск и проверка доставки

```bash
sudo systemctl enable --now televk
sudo systemctl status televk --no-pager
sudo journalctl -u televk -n 100 --no-pager
```

В группе появится стартовое уведомление. `/status` показывает состояние. `/chats` возвращает диалоги и `peer_id`; `/chat PEER_ID` создаёт тему заранее. Без этого темы возникают по новым сообщениям сами.

До запуска полного архива выполни проверки из `ACCEPTANCE.md`: текст, фото, файл в обе стороны, reply, прочтение, mute и перезапуск. Реальная проверка с другим аккаунтом должна быть согласована с собеседником; обычный `probe` этого не делает.

После первого успешного подключения хранится исходный курсор. При перезапуске используется сохранённая позиция: это не новое подключение «с нуля». Не удаляй базу для рядового обновления или исправления токена — потеряются соответствия тем и границы получения.

## 7. Ошибки и обслуживание

`/dlq` показывает до 20 последних `dead`/`uncertain`. `dead` означает явный отказ или исчерпание повторов; после исправления — `/retry_dlq ID`. `uncertain` означает неизвестный результат внешней отправки. Сначала проверь фактическое сообщение. `/retry_dlq ID force` разрешает повтор с риском дубля; другие уже доставленные части не повторяются.

В этой первой версии нет отдельной команды ручного признания неопределённой отправки успешно доставленной. Если сообщение явно доставлено, но задача осталась `uncertain`, не делай `force` только ради очистки статуса: она останется в очереди диагностики и может блокировать свою очередь данного чата. Разрешение такого случая без повторной отправки требует отдельной проверки соответствий в SQLite при остановленном сервисе. Это эксплуатационное ограничение пилота, не повод удалять базу целиком.

Если создание темы имело неопределённый результат, бот не создаёт следующую тему вслепую. Найди уже созданную тему и отправь в ней `/bind PEER_ID`. Если её точно нет, создай тему вручную и привяжи. При ошибках `message thread not found` сначала проверь группу и тему; перепривязка уже связанного peer к другому thread в этой версии специально запрещена.

Отказ VK приостанавливает соответствующую работу и оставляет сообщения в очереди. Исправь токен/доступ, останови сервис, выполни `probe` и при необходимости `probe --send-test`, затем запускай заново. При ошибке слишком старого курсора предусмотрена фоновая сверка доступной истории; `/resync` запускает её вручную. Она не может восстановить сообщения, которые исчезли из доступной истории.

```bash
sudo systemctl stop televk
# Исправить конфигурацию или секреты локальным редактором, сохранив права 600.
cd /opt/televk
sudo -u televk .venv/bin/python -m televk --config /etc/televk/config.json probe
sudo -u televk .venv/bin/python -m televk --config /etc/televk/config.json probe --send-test
sudo systemctl reset-failed televk
sudo systemctl start televk
```

Статус `active` у systemd означает работающий процесс, а не успешность всех API: смотри `/status`, возраст очереди и время последнего успешного запроса. Watchdog проверяет отзывчивость процесса, не интернет-соединение.

## 8. Резервная копия и ручное обновление

Останови сервис; единственная БД может использоваться только одним процессом CLI/run одновременно:

```bash
sudo systemctl stop televk
cd /opt/televk
sudo -u televk .venv/bin/python -m televk --config /etc/televk/config.json \
  backup /var/lib/televk/backup-before-update.sqlite3
```

Если файл уже существует, команда откажется его перезаписывать. Копию нужно отдельно перенести в защищённое хранилище; также сохрани `/etc/televk` и саму предыдущую версию кода. Бэкапы базы и секретов не шифруются этой утилитой. Копировать только `.sqlite3` во время записи, забывая WAL, нельзя — используется штатная SQLite backup API при остановленном сервисе.

Обновление ручное: проверить заметки к новой версии, сохранить текущую установку, собрать новый virtualenv и прогнать тесты, затем заменить только код/окружение. **Не запускать установщик первой установки поверх работающего TeleVK.** Состояние `/var/lib/televk` и секреты `/etc/televk` сохраняются; перед схемными изменениями нужна предусмотренная той версией миграция. Автоматическая миграция из telemax не предусмотрена.

`/updates` не обращается к PyPI. Python-зависимости проверяются по стабильным numeric tags соответствующих GitHub-репозиториев; VK schema, curl и systemd — также через GitHub. Локальные версии Python и SQLite только показываются, потому что ими управляет ОС. Для большинства библиотек «крупная» — смена major; до 1.0 — minor; для systemd — новая числовая серия. У certificate bundle смена календарного года не считается major. Наличие upstream-релиза не означает, что пакет ОС без исправлений: дистрибутивы могут переносить патчи. Проверка не устанавливает обновления и не анализирует CVE.

Сетевые отказы источников отображаются как `НЕ ПРОВЕРЕНО`. Автоматическое уведомление отправляется при новом наборе обнаруженных крупных обновлений; оно не повторяется бесконечно при каждом опросе. Полный результат можно запросить вручную. Необнаруженное изменение политики доступа VK или несовместимый minor-релиз такая проверка гарантированно предсказать не может.
